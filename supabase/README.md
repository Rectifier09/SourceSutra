# SourceSutra backend (Supabase)

This folder is the backend. It's mostly the Postgres schema + a few functions; the
REST/GraphQL API, auth, and storage are generated by Supabase (see `../bizlogic.md` §B.0).

**What's here right now:**

| File | What it is |
|---|---|
| `migrations/0001_core.sql` | Core tables, read RLS, the `award_quote` / `reject_quote` functions, overall-status view *(Step #1 — award proof)* |
| `migrations/0002_auth.sql` | Auth integration: `profiles` + `buyer_accounts`, signup provisioning trigger, onboarding write-guard, write RLS policies, `v_me` *(Phase 0 — auth & accounts)* |
| `migrations/0003_sourcing.sql` | Sourcing core: `publish_rfq` / `submit_quote` / `set_quote_triage` / `foreclose` / `reopen` / `lapse` / `invite_supplier` / `match_count`, the `invitations` table, and the rescoped `rfqs_read` *(Phase 2 — marketplace core)* |
| `migrations/0004_onboarding.sql` | Verification pipeline: `documents` + `certifications` + `identity_checks` (OTP result-only/masked), full badge vocabulary (`cert_badge`), `submit_section` (V3/V4/V5) + reviewer `review_section`, any-edit-reopens trigger, progress curve, `domain_events` outbox *(Phase 1 — onboarding & verification)* |
| `migrations/0005_notifications.sql` | Notifications (in-app + email) driven by event triggers → a single fan-out consumer; `respond_invitation` + `v_my_invitations` (Invitations tab); pg_cron schedule for the lapse sweeper *(Phase 3 — notifications & invitations)* |
| `migrations/0006_phase1_demo.sql` | **BP-1 demo shim (additive, removable):** `demo_verify_my_section` (self-serve auto-approve, reuses `review_section`) + exposes `v_supplier_overall` to the app (security_invoker + grant). Drop when the reviewer console lands. *(front-end BP-1)* |
| `tests/0001_award_test.sql` | pgTAP: the §A.7/§A.11 award invariants (atomic, idempotent, one-shot, RLS) — 20 assertions |
| `tests/0002_auth_test.sql` | pgTAP: signup provisioning, write policies, self-verify block, Financials lock — 14 assertions |
| `tests/0003_sourcing_test.sql` | pgTAP: publish → submit → triage → award loop, eligibility (verified/invite), foreclose/reopen/lapse, match-count — 37 assertions |
| `tests/0004_onboarding_test.sql` | pgTAP: full badge vocabulary, progress curve, submit gates, remediation→resubmit→verified, edit-reopens, masked Aadhaar, events, doc/identity RLS — 37 assertions |
| `tests/0005_notifications_test.sql` | pgTAP: publish fan-out (verified-only), new-application/award/close/foreclose/lapse/reopen notices, invite→respond→Invitations tab, notification RLS — 20 assertions |
| `tests/0006_phase1_demo_test.sql` | pgTAP: self-serve submit + auto-verify → Onboarding Completed; shim refuses a non-submitted section / non-supplier — 8 assertions |
| `seed.sql` | **BP-1 loginable demo cast** (email/password `sourcesutra`): buyer + 2 verified suppliers + 1 un-onboarded supplier + a live RFQ with two quotes + a draft |

Everything below runs **locally in Docker** — no cloud account is needed to run the proofs.

## 2. Run the proof (local, ~2 min)

From the repo root (`C:\workspace\SourceSutra`), in PowerShell:

```powershell
supabase init          # creates supabase/config.toml (leaves these files intact) — first time only
supabase start         # boots the local stack in Docker (first run pulls images)
supabase db reset       # applies migrations 0001–0006 + seed.sql from scratch
supabase test db        # runs the pgTAP tests  ->  expect: 136 passing (20 + 14 + 37 + 37 + 20 + 8)
```

Green `ok` lines from `supabase test db` = the "logic-in-Postgres" bet is validated:
the award transaction is atomic/idempotent/one-shot, signup provisions a full account,
and RLS + the onboarding guard are enforced by the database (no self-verify, Financials
locked until Identity).

## 2b. Verifying without Docker (Supabase SQL Editor)

If you're using a cloud project instead of the local stack: apply the two migrations in the
SQL Editor (`0001_core.sql` then `0002_auth.sql` — DDL, so they say *"Success. No rows returned"*,
which is correct), then paste and run **`verify_in_editor.sql`** (it lives next to the migrations,
outside `tests/`, so `supabase test db` doesn't try to run it as a pgTAP file).

> ⚠️ Don't run the `tests/0001_*` / `tests/0002_*` pgTAP files in the SQL Editor — those emit their
> results as many intermediate result sets, and the editor only shows the **last** statement
> (`rollback;`), so they misleadingly read *"Success. No rows returned"* whether they pass or fail.
> `verify_in_editor.sql` is built for the editor: its last statement **is** a PASS/FAIL grid, so you
> can actually read the outcome. Use `supabase test db` (local) for the full pgTAP run.

## Signup metadata contract (Phase 0)

The frontend/mobile passes these fields in the Supabase Auth signup `data` (they land in
`auth.users.raw_user_meta_data`), and the provisioning trigger builds the account from them:

```jsonc
// supplier signup (Google)                // buyer signup (Google or email/password)
{ "role": "supplier",                       { "role": "buyer",
  "full_name": "Suresh Anand",                "full_name": "Priya Menon",
  "company": "Anand Knitfab" }                "company": "Vardhman Textiles",
                                              "phone": "+91 …",
                                              "products_sourced": ["Knitwear","Denim"],
                                              "consent_version": "v1" }   // required for buyers
```

`role` defaults to `buyer` if omitted. After signup, the app reads `select * from v_me` to get
the caller's profile + org + role.

**Poke around:** `supabase start` prints a **Studio URL** (http://localhost:54323). Open it →
Table editor to see the seed data; SQL editor to try `select award_quote('90000000-0000-0000-0000-000000000002');`
against the seeded RFQ.

Stop the stack when done: `supabase stop`.

> If `supabase init` says "already initialized," that's fine — it just means `config.toml` exists.

## 3. Cloud accounts — set up now so later phases are unblocked (NOT needed for Step #1)

You can skip this until we start Phase 0, but here's the checklist so nothing blocks you later.

### Supabase (cloud)
1. Create an account at <https://supabase.com> (GitHub login is easiest).
2. **New project** → pick region **South Asia (Mumbai) / ap-south-1** (closest to users + future mobile).
   Save the **database password** it generates.
3. From the dashboard note: **Project ref**, **Project URL**, and the **anon** + **service_role** API keys
   (Settings → API). We'll put these in env vars later — never commit `service_role`.
4. Link your local repo to it (when we deploy):
   ```powershell
   supabase login
   supabase link --project-ref <your-project-ref>
   supabase db push          # applies local migrations to the cloud project
   ```

### Vercel (frontend host — only when we build the Next.js app)
1. Create an account at <https://vercel.com> (GitHub login).
2. Nothing to deploy yet. When the web app exists, you'll import the repo and set two env vars:
   `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (from the Supabase API settings above).
3. Vercel auto-deploys on every push + gives a preview URL per PR. No server config needed.

### GitHub (CI — later)
The deploy pipeline (`supabase db push` + `supabase functions deploy`, then Vercel) will need repo
secrets: `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`. We'll add these when
we wire CI.
